Executive summary
This report presents a tested Python backend for a Security Operations Centre alert queue. It separates routine
FIFO work from HIGH/CRITICAL priority work, uses an array-backed LIFO action stack, indexes current records
by identifier, and publishes immutable lifecycle events to subscribed analysts.
The implementation includes 24 tests, explicit capacity and validation errors, stable heap tie-breaking by severity
and receive time, and two educational sorting and two shortest-path algorithms. Actual performance
measurements and memory allocations are reported alongside Big-O analysis. The measured results show why
implementation constants and memory overhead must be considered with asymptotic growth.
The prototype is intentionally in-memory and single-process. It demonstrates the assignment's backend logic,
not a production-ready SOC platform; durable persistence, asynchronous delivery, authentication and
distributed scheduling are recommended next steps.

1. Introduction and requirements interpretation
This report designs, implements and evaluates a small backend for a Security Operations Centre (SOC) alert-
management service. The scenario in the Pearson brief has two competing operational needs: routine events
must be retained and processed in arrival order, while high-severity incidents must move ahead of lower-risk
work. The design therefore uses two explicit scheduling policies rather than forcing every alert through one
undifferentiated list. It also records alert identifiers, lifecycle status and timestamps, and publishes updates to
analyst observers (Pearson, 2024).
A SOC needs predictable ordering, safe state changes, traceability and bounded overload behaviour. A
theoretically efficient structure can still be slower in a particular runtime or consume more memory. The
evaluation combines asymptotic analysis, timing, traced-memory measurement and edge-case tests (Leiss, 2007;
Heineman, Pollice and Selkow, 2009).
The implementation uses Python 3.12 and pytest. Type hints, frozen data classes and exceptions keep the logic
readable. The linked queue, array stack and binary heap are implemented directly; locks, timestamps and the ID
dictionary use standard-library support (Python Software Foundation, 2024a; 2024b).
The report follows the four tasks and maps them to LO1–LO4. The assessment grid on pages 6–7 of the
supplied brief is also addressed: a concrete FIFO example, the software call stack, two sorting algorithms, two
shortest-path algorithms, imperative ADT specifications, encapsulation, the relation between ADTs and object

2. Task 1 — analysis and selection of data
structures
2.1 Data types and the alert record
An alert stores an ID, enumerated severity, timezone-aware received/updated timestamps and a lifecycle status
(QUEUED, IN_PROGRESS, RESOLVED or DISMISSED). The frozen Alert dataclass makes changes create
replacement snapshots rather than silently mutating a record. Python describes frozen dataclasses as read-only
emulation, not absolute memory immutability (Python Software Foundation, 2024a).
The chosen severity order is INFO < LOW < MEDIUM < HIGH < CRITICAL. The manager routes HIGH and
CRITICAL alerts to the priority heap; INFO, LOW and MEDIUM alerts enter the routine FIFO queue. This
threshold is a policy decision for the scenario, not a claim that all SOCs use identical severity taxonomies. The
received timestamp is retained separately from the update timestamp: the first explains when the source event
arrived, while the latter records when the system last changed its lifecycle state.


2.2 Arrays
Arrays store indexed elements and provide O(1) access by index. Traversal and unsorted search are O(n); middle
insertion/deletion is O(n) because elements shift. Dynamic arrays amortise append to O(1), although resizing
costs O(n). Arrays suit fixed tables, histograms, time buckets and caches (Cormen, Leiserson and Rivest, 1990;
Wirth, 2004).
The stack in this project is backed by a fixed-length Python list, which gives the demonstration direct array
indexing while enforcing a clear capacity. It preallocates a slot for each permitted history item. This trades
unused reserved slots for a simple overflow condition and predictable maximum history size. An ordinary Python
list is also used as a benchmark alternative, but that does not replace the custom array-backed stack
implementation.
  values = ["alert-A", "alert-B", "alert-C"]
  print(values[1])
  values.insert(1, "alert-X")
  print(values)

Actual interpreter output: `alert-B` followed by `['alert-A', 'alert-X', 'alert-B', 'alert-C']`. The example shows
constant-time indexed read and the visible shifting required by a middle insertion; it is an illustrative operation,
not a performance measurement.


2.3 Linked lists
A singly linked list stores values in nodes with next references. With head and tail pointers, tail insertion and
head removal are O(1), while search and indexed access are O(n). A doubly linked list adds a previous pointer,
increasing storage but enabling O(1) removal of a known node. Linked lists grow without contiguous allocation
but incur pointer, allocation and cache-locality costs (Cormen, Leiserson and Rivest, 1990; Sedgewick, 1983).
The routine queue uses a singly linked representation with both head and tail. Enqueue links a new node after
the tail; dequeue advances the head. When the last node is removed, both head and tail are reset to None. This
final reset is essential: otherwise a later enqueue could attach to a detached node and the empty-to-non-empty
transition would corrupt the queue. A capacity check is performed before allocation, making overload explicit
rather than allowing an unbounded queue to consume memory indefinitely.

2.4 Stacks and LIFO behaviour
A stack exposes push, pop and peek at one end and follows last-in-first-out (LIFO). An array stack has O(1) top
operations and O(C) preallocated storage; a linked stack grows dynamically but adds node overhead. Stacks suit
undo histories, parsing, depth-first traversal and runtime calls (Sedgewick, 1983; Wirth, 2004).
The analyst-action history uses a bounded array stack. If an analyst records “acknowledge AUTH-100” and then
“assign EDR-501”, the next undo returns “assign EDR-501” first. This is LIFO because undo reverses the newest
action before the older action. The sample execution in Appendix B records that exact order. The bound is
intentional: it prevents the demonstration history from growing without limit, and a production system could
persist an action audit trail separately rather than treating an in-memory undo stack as the authoritative record.
A function call pushes a frame containing return information, arguments and local state. Nested calls push newer
frames; returning pops the newest frame and resumes its caller. Recursion therefore uses nested LIFO frames.
The application's ArrayStack illustrates the ordering principle but is not the Python interpreter's runtime stack.


2.5 Queues and FIFO behaviour
A queue inserts at the rear and removes from the front (FIFO). A linked queue with head/tail references
achieves O(1) enqueue and dequeue. A circular array can also provide O(1) operations but needs capacity and
full/empty handling. Removing index zero from a plain list shifts remaining elements, making a full drain O(n²)
(Cormen, Leiserson and Rivest, 1990).
A concrete FIFO example is the arrival sequence A, B, C. Enqueue(A), enqueue(B), enqueue(C) yields the queue
[A, B, C]; three consecutive dequeue operations return A, then B, then C. A SOC routine stream uses this rule to
preserve fairness and traceability among events assigned to the routine path. It does not mean the whole
platform is globally FIFO: high-severity incidents are intentionally handled by a separate priority policy.
  queue = LinkedQueue()
  queue.enqueue("A")
  queue.enqueue("B")
  queue.enqueue("C")
  print([queue.dequeue() for _ in range(3)])

Output from the custom queue's same operation: `['A', 'B', 'C']`. The order is independent of the contents of the
alert identifiers; it follows insertion order.

3. Task 2 — system design and formal ADT
specification
3.1 Event flow and stored information
An event source supplies an identifier, severity, receive time and source label. Ingress validation parses severity,
checks the identifier and confirms a timezone-aware received_at. The immutable Alert snapshot is stored in the
identifier registry and routed to one pending structure: HIGH/CRITICAL to the priority heap, and lower levels to
the routine linked queue. The registry is the current snapshot; queue and heap entries select pending work.




                                                          Figure 1. SOC event flow

Events pass from heterogeneous sources through validation and the identifier registry, then split into priority and routine scheduling. Both
feed one processor. State changes publish lifecycle events to analyst subscribers; the bounded stack tracks the latest analyst actions.

Identifiers are unique within the manager. `_by_id` maps an identifier to the current immutable Alert object,
enabling average O(1) retrieval and avoiding a linear scan. `received_at` is not overwritten when processing
begins; `updated_at` changes when the state moves to IN_PROGRESS, RESOLVED or DISMISSED. Both
timestamps must be timezone-aware to avoid comparing naive local times with UTC times. The benchmark and
examples use UTC-aware timestamps so ordering is explicit and reproducible.
Processing checks the priority heap first, otherwise dequeues the oldest routine alert. The registry snapshot
becomes IN_PROGRESS and an event is emitted. Later valid transitions replace the snapshot and refresh
updated_at. Dismissed queued alerts are skipped when encountered; this lazy cancellation avoids an O(n) queue
search but retains a stale node until it reaches the front.
AlertEvent notifications contain event type, alert snapshot and emission time. The manager copies subscribers
under its RLock and calls them after releasing it, avoiding arbitrary callbacks inside the critical section. Listener

3.2 UML class model and encapsulation




                                                       Figure 2. UML class diagram

The model separates immutable alert/event objects from the coordinator and its three custom data structures. Private fields and public
operations show the information-hiding boundary.

The Alert class owns the record's identity, severity, status and timestamps. AlertEvent is a separate immutable
notification. AlertManager coordinates the structures and holds `_by_id`, `_routine`, `_priority`,
`_analyst_actions`, `_listeners` and `_lock` as private members. LinkedQueue, PriorityAlertQueue and
ArrayStack each expose only their valid operations. The diagram is a class-level view of the teaching
implementation; it does not imply a database, network service or deployment topology that the code does not
contain.
Information hiding is implemented in several ways. Callers do not receive the queue nodes or heap list; fields are
prefixed as private implementation details and access is through enqueue/dequeue, add/pop and push/pop
methods. Frozen dataclasses prevent mutation of alert snapshots, and state transitions pass through
AlertManager rather than arbitrary field assignment. Exceptions make rejected operations observable without
returning ambiguous sentinel values. In combination, these decisions protect invariants: unique IDs, capacity
limits, valid severity values and legal lifecycle transitions.
Encapsulation lowers the number of places that must understand internal representation. If a future version
replaces LinkedQueue with a circular buffer, clients that only use the queue contract should not need to change.
If a database-backed repository replaces the in-memory dictionary, the same principle allows the coordinator to
continue using a find-by-ID interface. The main advantage is not hiding code for its own sake; it is making the
correctness boundary explicit and localising change (Liskov and Zilles, 1974).

Queue contracts preserve FIFO; stack contracts preserve LIFO. Priority order is severity descending, receive
time ascending, then insertion sequence ascending. Each accepted queued alert is registered and scheduled
once. Processing chooses priority work before routine work. These observable rules do not depend on linked-
node or heap-array representation.


3.4 ADTs and object orientation
An imperative ADT is a useful basis for object orientation because it groups a state model with operations that
control how the state changes. An object can realise that contract and prevent clients from depending on its
representation. The AlertManager and custom structures follow this style: public methods express permitted
actions, while private attributes preserve internal invariants. This is consistent with the ADT idea that clients
should use a defined interface rather than manipulate the representation directly (Liskov and Zilles, 1974).
However, ADTs alone do not constitute the whole of object-oriented programming. Object orientation may also
use subtype relationships, dynamic dispatch, inheritance and polymorphic interfaces. The implementation here
does not need a large inheritance hierarchy; composition is simpler because the manager owns and coordinates
queue, heap and stack objects. I therefore agree that imperative ADTs provide a strong conceptual foundation
for object-oriented design, but they are not a complete definition of every object-oriented mechanism. The
benefit is a disciplined boundary, not an assumption that every structure should inherit from a common base
class.

4. Task 3 — implementation, testing and
algorithm analysis
4.1 Implementation logic
The implementation is split into models.py, structures.py, manager.py, sorting.py and graph_algorithms.py. This
modular separation keeps domain validation out of pointer manipulation and keeps the coordinator from
exposing low-level heap details. Type hints document the intended generic values, and dataclasses reduce
boilerplate for value objects. The data structures are intentionally implemented directly so the code
demonstrates the algorithms rather than wrapping Python's deque or heapq for the assessed core operations.
The linked queue stores a head pointer, tail pointer, size and optional capacity. Its enqueue operation allocates
one node and links it at the tail. Dequeue saves the head value, advances the head, decrements size and clears
tail if the queue becomes empty. This makes both operations constant-time because no traversal is needed. The
structure has O(n) space for n nodes; the per-node object and pointer overhead is a real cost in a high-volume
system.
  def enqueue(self, value):
      if self._capacity is not None and self._size >= self._capacity:
          raise QueueFullError("queue capacity reached")
      node = _Node(value)
      if self._tail is None:
          self._head = self._tail = node
      else:
          self._tail.next = node
          self._tail = node
      self._size += 1

This extract is from structures.py. The capacity guard runs before allocation. The empty-queue branch sets both
head and tail to the new node, while the non-empty branch links after the existing tail. The test
`test_linked_queue_is_fifo_and_clears_tail_after_last_dequeue` drains the queue and then enqueues again,
verifying the important empty-to-non-empty transition.
The priority structure is a custom binary max-heap stored in a Python list. Each node has a parent at
floor((i−1)/2), a left child at 2i+1 and a right child at 2i+2. After insertion, sift-up exchanges the new entry with a
lower-ranked parent until the heap invariant is restored. After removal, the last entry replaces the root and sift-
down exchanges it with the larger child. Both repairs take O(log n) time because heap height is logarithmic. The
root is always the next item to process (Cormen, Leiserson and Rivest, 1990).
  def _priority_key(alert, sequence):
      return (int(alert.severity),
              -alert.received_at.timestamp(), -sequence)

  def pop(self):
      if not self._heap:
          raise QueueEmptyError("cannot pop from an empty priority queue")
      root = self._heap[0].alert
      last = self._heap.pop()
      if self._heap:
          self._heap[0] = last
          self._sift_down(0)
      return root

The key encodes the scheduling rule in one comparable tuple. A larger severity is preferred; for equal severities
a smaller timestamp produces a larger negative timestamp component; if both match, a smaller insertion
sequence wins. The counter also prevents Python from comparing Alert objects if two entries otherwise tie. This
preserves stable ordering for simultaneous arrivals, rather than leaving equal-priority order dependent on
incidental heap swaps.

4.2 Error handling, correctness and TDD
Tests were written before production code. The initial RED run failed at collection because the expected
soc_alerts modules were absent (results/tdd-red.txt). The first GREEN run passed 18 tests; six more checks were
added for heap peek, dismissed entries, invalid actions, action-stack overflow, concurrent ingestion and
algorithm edge cases. The current suite has 24 passing tests, preserving the red–green sequence (pytest
development team, 2026).
Error handling uses named exceptions instead of sentinel values. QueueEmptyError and StackEmptyError
distinguish invalid removal from a valid empty value; QueueFullError and StackOverflowError report configured
capacity; DuplicateAlertError blocks ambiguous identifiers; InvalidSeverityError rejects unknown severity names;
AlertNotFoundError identifies absent records; and InvalidStatusTransitionError prevents illegal lifecycle changes.
Alert construction rejects empty IDs and naive timestamps. These failures are important in a SOC because
silently dropping an event or accepting an ambiguous identifier can damage traceability and response priority.
Observer exceptions are caught individually and added to listener_errors. This is deliberate fault isolation: a
failed subscriber should not cancel a successfully stored record or prevent the next subscriber from receiving an
event. The manager does not yet impose a retention limit on its diagnostic error list, so a production service
should send those errors to a bounded logging pipeline. Similarly, capacity errors are exposed to the caller; a
production ingress layer would need a retry/back-pressure policy rather than assuming that an alert has been
accepted when the capacity limit has been reached.

5.2 FIFO: linked queue versus Python list

                                                    Figure 3. FIFO end-to-end timing

Log-scale comparison of measured queue build-and-drain time for the custom linked queue and Python list front removal.

At 250 items the list cycle is faster (0.0225 ms against 0.0824 ms), and the linked queue remains slower at 1,000
and 4,000 items. At 16,000 items the result reverses: the linked queue takes 6.0389 ms while the list takes
15.2750 ms. The crossover is consistent with the list's O(n) front removal causing repeated element shifts and an
O(n²) full drain, while the linked queue performs one constant-time pointer update per removal. It also illustrates
why measuring small data sets alone could lead to the wrong structural conclusion.
The list is faster at modest sizes because C-level operations have lower constants than custom Python nodes. At
larger n, repeated shifts dominate. Memory matters too: at 5,000 values the list peaks at 191,952 bytes and the
linked queue at 391,992 bytes. A production system should also benchmark a circular array queue, which can
retain O(1) dequeue with better locality.


5.3 Priority scheduling: heap versus sorted list




                                                     Figure 4. Priority queue timing

Measured add-all/remove-all cycle comparing a custom binary max-heap with a dynamically maintained sorted list using bisect insertion.

Heap insertion/removal are O(log n), or O(n log n) for a full cycle. A bisect-maintained sorted list has O(log n)
search but O(n) insertion shifts, giving O(n²) total insertion work. Yet it is faster in these runs: 0.2286 vs 0.5712
ms at 250 and 52.17 vs 91.67 ms at 16,000. C-level bisect/list operations have lower constants than Python sift
loops.
The result does not prove that a sorted list scales better. At a much larger or more heavily updated queue,
quadratic shifting should become increasingly expensive; alternatively, a native heap implementation may
reduce the constant factor. The custom heap remains the defensible structure for the stated priority ADT
because it gives logarithmic insertion/removal, a predictable root selection rule and bounded repair work. If the

actual production workload has low queue sizes and very few insertions, a sorted list could be competitive, but it
should be selected only after a representative benchmark and a clear update-cost model.


5.4 Sorting algorithms




                                                      Figure 5. Sorting algorithm timing

Measured stable insertion sort versus iterative merge sort for the seeded random arrays at three sizes.

Insertion sort measured 0.1894, 5.2688 and 54.0763 ms at n = 100, 500 and 1,500; merge sort measured
0.1157, 0.6451 and 2.6409 ms. Insertion sort is O(n²) average/worst, while iterative merge sort is O(n log n)
time and O(n) extra space. Both are stable (Sedgewick, 1983; Cormen, Leiserson and Rivest, 1990).
Insertion sort remains useful for very small or nearly sorted arrays because it has low setup cost, good locality
and O(n) best-case behaviour when the input is already ordered. Merge sort is a better general choice for larger
unsorted batches where predictable O(n log n) performance outweighs the extra memory. The SOC scheduling
path does not sort the entire queue on every alert; the heap is preferable for incremental priority insertion and
removal. Sorting is included to demonstrate comparative analysis and could be useful for offline reporting or
exporting a time-window snapshot.

Peak tracemalloc bytes for one list and one custom linked queue containing 5,000 integer values.

The recorded peak traced allocations are 191,952 bytes for the Python list and 391,992 bytes for the linked

production load test would be needed to estimate deployment memory more completely (Python Software

5.6 Network shortest-path algorithms
The Pearson distinction criterion also asks for two shortest-path algorithms illustrated with examples. A SOC
network can be modelled as a weighted directed graph: vertices represent sensors, gateways, switches and
servers, and edge weights represent a simplified traversal cost or latency. Figure 7 contains a four-vertex
example. From Sensor to Server, the candidate route through Gateway then Switch costs 2 + 1 + 5 = 8; the
direct Gateway-to-Server alternative costs 2 + 8 = 10, and the Sensor-to-Switch route costs 4 + 5 = 9. Both
implemented algorithms return 8 on this non-negative graph.




                                                       TECHNICAL REPORT • 15
UNIT 19 / DATA STRUCTURES & ALGORITHMS                                    SOC ALERT MANAGEMENT




                                             Figure 7. Weighted SOC network shortest path

Illustrative positive-weight network. The highlighted route is Sensor → Gateway → Switch → Server and costs 8. The same graph is supplied
to both algorithms.

Dijkstra's algorithm repeatedly finalises the lowest-distance vertex and relaxes its outgoing edges. With an
adjacency list and a binary min-heap, its common sparse-graph bound is O((V+E) log V); the implementation uses
lazy duplicate heap entries and checks stale distances when they are removed. Its precondition is non-negative
edge weights. A negative edge can invalidate the greedy finalisation argument, so the implementation rejects
negative weights instead of returning a plausible but incorrect route (Dijkstra, 1959).
Bellman–Ford relaxes all edges up to V−1 times and uses a final pass to detect reachable negative cycles. Its
O(VE) time is slower on large sparse positive-weight graphs, but it supports negative edges (Bellman, 1958). The
implementation validates endpoints and stops early when a pass makes no change. Dijkstra suits non-negative
SOC network costs; Bellman–Ford is the more general diagnostic.


5.7 Trade-offs and three benefits of implementation independence
A key ADT trade-off is the balance between representation cost and operation guarantees. A linked queue uses
additional memory to make tail insertion and head removal O(1); a circular array queue can be more compact but
has a fixed or resizing capacity policy. An array stack is simple and fast but needs a capacity bound; a linked
stack grows dynamically but allocates nodes. A binary heap selects urgent work efficiently, but locating and
reprioritising an arbitrary alert is not O(1): a production design would need an ID-to-heap-index map or lazy
invalidation/version tokens. Making those trade-offs explicit is part of specifying the ADT rather than an
afterthought (Leiss, 2007; Heineman, Pollice and Selkow, 2009).
Implementation independence enables substitution (for example, linked queue to ring buffer),
optimisation/portability without rewriting clients, and reusable contract tests across alternative
implementations. It also localises invariants and reduces coupling between the SOC UI, scheduler and storage.

6. Security, reliability and operational
limitations
The prototype enforces basic data integrity: unique non-empty IDs, enumerated severity, timezone-aware
timestamps, explicit lifecycle transitions and capacity bounds. Those controls prevent several classes of
accidental corruption, but they do not provide authentication, authorisation, encryption, input provenance
verification or durable audit retention. A real SOC would need authenticated event sources, schema validation,
tenant separation, access control by analyst role, tamper-evident audit records and a defined retention policy.
The current source field is descriptive metadata, not cryptographic proof that an event came from a trusted
sensor.
The dictionary and queues are process-local. A restart loses pending work; multiple service instances do not
share priority order. RLock is not a distributed lock or transaction coordinator, and callbacks are not durably
retried. These limits suit the assignment scope but must be addressed before deployment.
The next step is a durable event log and transactional repository. An asynchronous bus could deliver analyst
updates with acknowledgements, bounded retries and dead-letter handling. Horizontal scaling would require a
shared broker or partitioned scheduler with explicit ordering semantics. Metrics should include queue depth,
oldest-event age, severity latency, rejected capacity events and delivery failures; load tests should cover
sustained rates and burst recovery.
Strict priority can starve routine work during a sustained incident flood. It is implemented because the
assignment requires high-severity precedence. A production scheduler may add ageing, weighted fairness or a
maximum priority burst, but that changes the ADT selection contract and must be agreed and tested explicitly.


7. Conclusion and recommendations
The backend meets the SOC scenario's two ordering requirements with separate ADTs. A linked FIFO queue
retains routine arrival order; a custom binary max-heap selects HIGH/CRITICAL alerts first and resolves ties by
earliest timestamp and stable insertion order. An array stack records analyst actions in LIFO order. An ID
dictionary supports retrieval, immutable snapshots protect records, and observer events provide in-process
updates.
The 24 tests cover normal and error cases, stability, state transitions, capacity and concurrent ingestion. At n =
16,000 the linked queue beats list front-removal but uses more traced memory. The heap has better asymptotic
growth than the sorted list, although the latter is faster in this Python run; merge sort scales better than
insertion sort. These results show why Big-O, timing and memory must be read together.
For the assignment scenario, the selected structures are justified by their operation contracts and ordering
guarantees. For production, the recommendation is to preserve those interfaces while adding durable storage,
asynchronous analyst delivery, workload-specific benchmarking, admission/back-pressure controls, metrics and
a starvation policy. The ADT boundary makes those improvements possible without exposing every consumer to
the internal representation. The project therefore meets the core brief as a tested teaching backend while
making its operational limits explicit.
