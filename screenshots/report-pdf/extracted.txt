Executive summary
This report presents a tested Python backend for a Security Operations Centre alert queue. It separates routine FIFO work
from HIGH/CRITICAL priority work, uses an array-backed LIFO action stack, indexes current records by identifier, and
publishes immutable lifecycle events to subscribed analysts.
The implementation includes 24 tests, explicit capacity and validation errors, stable heap tie-breaking by severity and receive
time, and two educational sorting and two shortest-path algorithms. Actual performance measurements and memory
allocations are reported alongside Big-O analysis. The measured results show why implementation constants and memory
overhead must be considered with asymptotic growth.
The prototype is intentionally in-memory and single-process. It demonstrates the assignment's backend logic, not a
production-ready SOC platform; durable persistence, asynchronous delivery, authentication and distributed scheduling are
recommended next steps.

1. Introduction and requirements interpretation
This report designs, implements and evaluates a small backend for a Security Operations Centre (SOC) alert-management
service. The scenario in the Pearson brief has two competing operational needs: routine events must be retained and
processed in arrival order, while high-severity incidents must move ahead of lower-risk work. The design therefore uses two
explicit scheduling policies rather than forcing every alert through one undifferentiated list. It also records alert identifiers,
lifecycle status and timestamps, and publishes updates to analyst observers (Pearson, 2024).
A SOC needs predictable ordering, safe state changes, traceability and bounded overload behaviour. A theoretically efficient
structure can still be slower in a particular runtime or consume more memory. The evaluation combines asymptotic analysis,
timing, traced-memory measurement and edge-case tests (Leiss, 2007; Heineman, Pollice and Selkow, 2009).
The implementation is written in Python 3.12 with pytest. Python was selected because its type annotations, immutable data
classes, exceptions and test ecosystem make the data-structure logic accessible to inspect while keeping the deliverable
executable with a short command. The linked queue, array stack and binary heap are implemented in the project rather than
delegated to deque or heapq, so their invariants and algorithms are visible. Standard-library locks, datetime values and
dictionaries are used for coordination, time representation and identifier indexing; those facilities are not the assessed
scheduling structures (Python Software Foundation, 2024a; 2024b).
The report follows the four tasks and maps them to LO1–LO4. The assessment grid on pages 6–7 of the supplied brief is also
addressed: a concrete FIFO example, the software call stack, two sorting algorithms, two shortest-path algorithms,
imperative ADT specifications, encapsulation, the relation between ADTs and object orientation, trade-offs, and benefits of
implementation-independent designs. Full source files, test evidence, benchmark data and diagram source are retained under
the project appendices and evidence folders.

2. Task 1 — analysis and selection of data structures
2.1 Data types and the alert record
An alert is a structured record, not a single scalar. Its identifier is a string used for retrieval, severity is an enumerated value,
and received_at and updated_at are timezone-aware timestamps. Status is an enumeration with QUEUED, IN_PROGRESS,
RESOLVED and DISMISSED states. This makes invalid values harder to introduce than if every field were an unrestricted
string. The Alert object is frozen: a change creates a replacement snapshot, so a callback or caller holding an older snapshot
cannot silently mutate the manager's current record. Python documents frozen data classes as an emulation of read-only
instances rather than a claim of absolute memory immutability (Python Software Foundation, 2024a).
The chosen severity order is INFO < LOW < MEDIUM < HIGH < CRITICAL. The manager routes HIGH and CRITICAL alerts
to the priority heap; INFO, LOW and MEDIUM alerts enter the routine FIFO queue. This threshold is a policy decision for the
scenario, not a claim that all SOCs use identical severity taxonomies. The received timestamp is retained separately from the
update timestamp: the first explains when the source event arrived, while the latter records when the system last changed its
lifecycle state.

2.2 Arrays
An array stores elements in indexed positions, normally in contiguous storage in low-level implementations. Its main
advantage is direct access by index: retrieving position i takes O(1) time. Traversal is O(n), searching an unsorted array is O(n),
and inserting or deleting near the front or middle can take O(n) because subsequent elements must shift. A dynamic array
adds capacity management and occasional resizing; amortised append is commonly O(1), although a resizing append can be
O(n). Arrays fit fixed-size tables, severity histograms, time buckets and caches where indexed access and locality matter
(Cormen, Leiserson and Rivest, 1990; Wirth, 2004).
The stack in this project is backed by a fixed-length Python list, which gives the demonstration direct array indexing while
enforcing a clear capacity. It preallocates a slot for each permitted history item. This trades unused reserved slots for a simple
overflow condition and predictable maximum history size. An ordinary Python list is also used as a benchmark alternative, but
that does not replace the custom array-backed stack implementation.
values = ["alert-A", "alert-B", "alert-C"]
print(values[1])
values.insert(1, "alert-X")
print(values)

Actual interpreter output: `alert-B` followed by `['alert-A', 'alert-X', 'alert-B', 'alert-C']`. The example shows constant-time
indexed read and the visible shifting required by a middle insertion; it is an illustrative operation, not a performance
measurement.

2.3 Linked lists
A linked list represents a sequence as nodes connected by references. In a singly linked list, each node stores a value and a
reference to its successor. With head and tail references, insertion at the tail and removal at the head are O(1); searching for
an arbitrary value and accessing the i-th item are O(n). A doubly linked list adds a previous reference, allowing removal of a
known node in O(1) but increasing per-node storage. Linked lists grow node by node and do not need a contiguous block, but
they incur pointer and allocation overhead and have weaker cache locality than arrays (Cormen, Leiserson and Rivest, 1990;
Sedgewick, 1983).
The routine queue uses a singly linked representation with both head and tail. Enqueue links a new node after the tail;
dequeue advances the head. When the last node is removed, both head and tail are reset to None. This final reset is essential:
otherwise a later enqueue could attach to a detached node and the empty-to-non-empty transition would corrupt the queue.
A capacity check is performed before allocation, making overload explicit rather than allowing an unbounded queue to
consume memory indefinitely.

2.4 Stacks and LIFO behaviour
A stack exposes access at one end, usually described by push, pop and peek. It follows last-in-first-out (LIFO): the most
recently added value is removed first. An array-backed stack offers O(1) push and pop while it has capacity and O(1) peek;
the storage cost is O(C) for a preallocated capacity C. A linked stack can grow dynamically and has O(1) top operations, but
each element adds a node and reference. Stacks suit nested operations, undo histories, parsing, depth-first traversal and
runtime call management (Sedgewick, 1983; Wirth, 2004).
The analyst-action history uses a bounded array stack. If an analyst records “acknowledge AUTH-100” and then “assign
EDR-501”, the next undo returns “assign EDR-501” first. This is LIFO because undo reverses the newest action before the
older action. The sample execution in Appendix B records that exact order. The bound is intentional: it prevents the
demonstration history from growing without limit, and a production system could persist an action audit trail separately
rather than treating an in-memory undo stack as the authoritative record.
A computer's function-call stack uses the same LIFO idea. On a call, a frame holds information needed to continue the caller,
such as arguments, local variables, saved registers and a return location. A nested call pushes a newer frame; when the
function returns, the most recent frame is removed and execution resumes in the caller. Recursive calls therefore create
nested frames. This explains the P2 memory-stack criterion, but the application-level ArrayStack is not the Python
interpreter's runtime call stack. The two share an ordering principle, not storage ownership or implementation
responsibilities.

2.5 Queues and FIFO behaviour
A queue inserts at the rear and removes from the front. It follows first-in-first-out (FIFO): the earliest enqueued item is the
next one removed. A linked queue with head and tail achieves O(1) enqueue and dequeue. A circular array queue can also
provide O(1) operations by advancing modular head and tail indices, but it needs capacity management and correct
full/empty disambiguation. A plain array/list that removes the first element must shift the remaining elements, which makes
each front removal O(n) and a complete drain O(n²) (Cormen, Leiserson and Rivest, 1990).
A concrete FIFO example is the arrival sequence A, B, C. Enqueue(A), enqueue(B), enqueue(C) yields the queue [A, B, C];
three consecutive dequeue operations return A, then B, then C. A SOC routine stream uses this rule to preserve fairness and
traceability among events assigned to the routine path. It does not mean the whole platform is globally FIFO: high-severity
incidents are intentionally handled by a separate priority policy.
queue.enqueue("A")
queue.enqueue("B")
queue.enqueue("C")
print([queue.dequeue() for _ in range(3)])

Output from the custom queue's same operation: `['A', 'B', 'C']`. The order is independent of the contents of the alert
identifiers; it follows insertion order.

The design uses structures for different access patterns rather than choosing one “best” structure. The ID dictionary provides
average O(1) lookup, the linked queue supports FIFO, the heap supports severity-first selection, and the stack supports LIFO
action history. Each structure is hidden behind a small operation set. This separation limits coupling: changing the queue
implementation does not require the analyst notification code to understand node pointers or heap indices.

3. Task 2 — system design and formal ADT specification
3.1 Event flow and stored information
An event source supplies an identifier, severity, receive time and source label. Ingress validation parses severity, checks the
identifier and confirms a timezone-aware received_at. The immutable Alert snapshot is stored in the identifier registry and
routed to one pending structure: HIGH/CRITICAL to the priority heap, and lower levels to the routine linked queue. The
registry is the current snapshot; queue and heap entries select pending work.
Figure 1. SOC event flow
Events pass from heterogeneous sources through validation and the identifier registry, then split into priority and routine scheduling. Both
feed one processor. State changes publish lifecycle events to analyst subscribers; the bounded stack tracks the latest analyst actions.

Identifiers are unique within the manager. `_by_id` maps an identifier to the current immutable Alert object, enabling average
O(1) retrieval and avoiding a linear scan. `received_at` is not overwritten when processing begins; `updated_at` changes
when the state moves to IN_PROGRESS, RESOLVED or DISMISSED. Both timestamps must be timezone-aware to avoid
comparing naive local times with UTC times. The benchmark and examples use UTC-aware timestamps so ordering is explicit
and reproducible.
When an analyst asks to process the next item, the manager first checks the priority heap. If a priority entry exists, its
maximum-ranked alert is selected; otherwise, the oldest routine entry is dequeued. Processing replaces the snapshot with an
IN_PROGRESS version and emits an event. A permitted later transition, such as IN_PROGRESS to RESOLVED, creates
another snapshot with a new update timestamp. A queued alert may be dismissed; it remains physically in its queue until
encountered, at which point the processor skips it because the registry no longer marks it QUEUED. This lazy cancellation
avoids an O(n) search through the linked queue, at the cost of retaining a stale node until it reaches the front.
Analyst updates are represented by AlertEvent objects and a subscriber list. A notification includes the event type, a snapshot
of the alert and an emission timestamp. The manager copies the listener list while locked, then calls the observers after
releasing its RLock. This prevents arbitrary callback code from running inside the manager's critical section and reduces the
risk of deadlock or a slow user interface blocking ingestion. Observer exceptions are isolated and recorded for diagnostics;
one disconnected analyst listener does not undo an accepted alert. In an operational deployment, this in-process observer
mechanism would normally feed an asynchronous message broker or WebSocket gateway and a durable audit log.

3.2 UML class model and encapsulation
Figure 2. UML class diagram
The model separates immutable alert/event objects from the coordinator and its three custom data structures. Private fields and public
operations show the information-hiding boundary.

The Alert class owns the record's identity, severity, status and timestamps. AlertEvent is a separate immutable notification.
AlertManager coordinates the structures and holds `_by_id`, `_routine`, `_priority`, `_analyst_actions`, `_listeners` and
`_lock` as private members. LinkedQueue, PriorityAlertQueue and ArrayStack each expose only their valid operations. The
diagram is a class-level view of the teaching implementation; it does not imply a database, network service or deployment
topology that the code does not contain.
Information hiding is implemented in several ways. Callers do not receive the queue nodes or heap list; fields are prefixed as
private implementation details and access is through enqueue/dequeue, add/pop and push/pop methods. Frozen dataclasses
prevent mutation of alert snapshots, and state transitions pass through AlertManager rather than arbitrary field assignment.
Exceptions make rejected operations observable without returning ambiguous sentinel values. In combination, these
decisions protect invariants: unique IDs, capacity limits, valid severity values and legal lifecycle transitions.

Encapsulation lowers the number of places that must understand internal representation. If a future version replaces
LinkedQueue with a circular buffer, clients that only use the queue contract should not need to change. If a database-backed
repository replaces the in-memory dictionary, the same principle allows the coordinator to continue using a find-by-ID
interface. The main advantage is not hiding code for its own sake; it is making the correctness boundary explicit and localising
change (Liskov and Zilles, 1974).

3.3 Imperative ADT specification
An abstract data type (ADT) describes the values and observable operations of a type while leaving its concrete
representation open. The following imperative contracts state the preconditions and postconditions for each operation. Let Q
be the routine sequence ordered from front to rear; P be the set of priority entries; S be the stack sequence ordered bottom
to top; and M be the identifier-to-alert map. Let cap(X) denote the maximum size configured for structure X. For a priority
entry, rank(a) = (severity(a), −epoch(received_at(a)), −sequence(a)); the lexicographically greatest rank wins. The monotonically
increasing insertion sequence makes equal-severity/equal-timestamp entries stable.

The queue contracts preserve FIFO because enqueue appends and dequeue removes only the head. The stack contracts
preserve LIFO because push appends and pop removes only the last element. The priority contracts impose a total order:
severity descends, received time ascends, then insertion sequence ascends. The manager invariant is that each newly
accepted queued alert is registered once and scheduled once. Its process operation chooses the priority structure before the
routine queue, so urgent items are not delayed by routine backlog. The specification defines observable behaviour
independently from the linked node and heap-array representations.

3.4 ADTs and object orientation
An imperative ADT is a useful basis for object orientation because it groups a state model with operations that control how
the state changes. An object can realise that contract and prevent clients from depending on its representation. The
AlertManager and custom structures follow this style: public methods express permitted actions, while private attributes
preserve internal invariants. This is consistent with the ADT idea that clients should use a defined interface rather than
manipulate the representation directly (Liskov and Zilles, 1974).
However, ADTs alone do not constitute the whole of object-oriented programming. Object orientation may also use subtype
relationships, dynamic dispatch, inheritance and polymorphic interfaces. The implementation here does not need a large
inheritance hierarchy; composition is simpler because the manager owns and coordinates queue, heap and stack objects. I
therefore agree that imperative ADTs provide a strong conceptual foundation for object-oriented design, but they are not a
complete definition of every object-oriented mechanism. The benefit is a disciplined boundary, not an assumption that every

4. Task 3 — implementation, testing and algorithm analysis
4.1 Implementation logic
The implementation is split into models.py, structures.py, manager.py, sorting.py and graph_algorithms.py. This modular
separation keeps domain validation out of pointer manipulation and keeps the coordinator from exposing low-level heap
details. Type hints document the intended generic values, and dataclasses reduce boilerplate for value objects. The data
structures are intentionally implemented directly so the code demonstrates the algorithms rather than wrapping Python's
deque or heapq for the assessed core operations.
The linked queue stores a head pointer, tail pointer, size and optional capacity. Its enqueue operation allocates one node and
links it at the tail. Dequeue saves the head value, advances the head, decrements size and clears tail if the queue becomes
empty. This makes both operations constant-time because no traversal is needed. The structure has O(n) space for n nodes;
the per-node object and pointer overhead is a real cost in a high-volume system.
def enqueue(self, value):
if self._capacity is not None and self._size >= self._capacity:
raise QueueFullError("queue capacity reached")
node = _Node(value)
if self._tail is None:
self._head = self._tail = node
else:
self._tail.next = node
self._tail = node
self._size += 1

This extract is from structures.py. The capacity guard runs before allocation. The empty-queue branch sets both head and tail
to the new node, while the non-empty branch links after the existing tail. The test
`test_linked_queue_is_fifo_and_clears_tail_after_last_dequeue` drains the queue and then enqueues again, verifying the
important empty-to-non-empty transition.
The priority structure is a custom binary max-heap stored in a Python list. Each node has a parent at floor((i−1)/2), a left child
at 2i+1 and a right child at 2i+2. After insertion, sift-up exchanges the new entry with a lower-ranked parent until the heap
invariant is restored. After removal, the last entry replaces the root and sift-down exchanges it with the larger child. Both
repairs take O(log n) time because heap height is logarithmic. The root is always the next item to process (Cormen, Leiserson
and Rivest, 1990).

The key encodes the scheduling rule in one comparable tuple. A larger severity is preferred; for equal severities a smaller
timestamp produces a larger negative timestamp component; if both match, a smaller insertion sequence wins. The counter
also prevents Python from comparing Alert objects if two entries otherwise tie. This preserves stable ordering for
simultaneous arrivals, rather than leaving equal-priority order dependent on incidental heap swaps.
The manager validates severity and identifiers before modifying storage. A dictionary supports lookup; a queue or heap
records the pending work order. `process_next` chooses from the heap first and the routine queue second, updates the

mapping: QUEUED can become IN_PROGRESS or DISMISSED; IN_PROGRESS can become RESOLVED or DISMISSED;
terminal states cannot move again. This protects the audit meaning of the lifecycle rather than allowing arbitrary status

4.2 Error handling, correctness and TDD
Tests were written before production code. The initial RED run failed at collection because the expected soc_alerts modules
were absent (results/tdd-red.txt). The first GREEN run passed 18 tests; six more checks were added for heap peek, dismissed
entries, invalid actions, action-stack overflow, concurrent ingestion and algorithm edge cases. The current suite has 24
passing tests, preserving the red–green sequence (pytest development team, 2026).
Error handling uses named exceptions instead of sentinel values. QueueEmptyError and StackEmptyError distinguish invalid
removal from a valid empty value; QueueFullError and StackOverflowError report configured capacity; DuplicateAlertError
blocks ambiguous identifiers; InvalidSeverityError rejects unknown severity names; AlertNotFoundError identifies absent
records; and InvalidStatusTransitionError prevents illegal lifecycle changes. Alert construction rejects empty IDs and naive
timestamps. These failures are important in a SOC because silently dropping an event or accepting an ambiguous identifier
can damage traceability and response priority.
Observer exceptions are caught individually and added to listener_errors. This is deliberate fault isolation: a failed subscriber
should not cancel a successfully stored record or prevent the next subscriber from receiving an event. The manager does not
yet impose a retention limit on its diagnostic error list, so a production service should send those errors to a bounded logging
pipeline. Similarly, capacity errors are exposed to the caller; a production ingress layer would need a retry/back-pressure
policy rather than assuming that an alert has been accepted when the capacity limit has been reached.

5.1 Measurement design
Three complementary approaches were used. First, asymptotic analysis predicts how operation counts grow as input size
increases. Second, empirical timing measures complete data-structure or algorithm workloads at several sizes using

5.2 FIFO: linked queue versus Python list
Figure 3. FIFO end-to-end timing
Log-scale comparison of measured queue build-and-drain time for the custom linked queue and Python list front removal.

At 250 items the list cycle is faster (0.0225 ms against 0.0824 ms), and the linked queue remains slower at 1,000 and 4,000
items. At 16,000 items the result reverses: the linked queue takes 6.0389 ms while the list takes 15.2750 ms. The crossover
is consistent with the list's O(n) front removal causing repeated element shifts and an O(n²) full drain, while the linked queue
performs one constant-time pointer update per removal. It also illustrates why measuring small data sets alone could lead to
the wrong structural conclusion.
The linked queue is not a universal runtime winner. Python's list operations are implemented in C and have lower constant
factors than the custom Python node operations. For modest queues, those constants dominate. The linked queue's benefit
becomes visible as repeated front-removal cost accumulates. The memory measurement also matters: at 5,000 values, the list
peak is 191,952 bytes and the linked queue peak is 391,992 bytes. The node-per-item design uses roughly twice the traced
allocation in this experiment. A production system with a predictable maximum queue size might therefore benchmark a
circular array queue as a third option; that design can retain O(1) dequeue while improving locality and reducing per-node
overhead.

5.3 Priority scheduling: heap versus sorted list
Figure 4. Priority queue timing
Measured add-all/remove-all cycle comparing a custom binary max-heap with a dynamically maintained sorted list using bisect insertion.

The heap has O(log n) insertion and removal, giving O(n log n) total work for a complete load-and-drain cycle. The alternative
inserts each new tuple into a sorted Python list by binary search and then removes the largest item from the end. Although
the search is O(log n), the insertion shifts later references and is O(n); total insertion cost is O(n²). Yet the measured sorted-list
cycle is faster at every tested size: 0.2286 ms versus 0.5712 ms at 250, and 52.1700 ms versus 91.6699 ms at 16,000. The
custom heap executes sift logic in Python, while bisect and list movement use optimized runtime code. This is a direct
example of an implementation-level crossover not being guaranteed by Big-O alone.
The result does not prove that a sorted list scales better. At a much larger or more heavily updated queue, quadratic shifting
should become increasingly expensive; alternatively, a native heap implementation may reduce the constant factor. The
custom heap remains the defensible structure for the stated priority ADT because it gives logarithmic insertion/removal, a
predictable root selection rule and bounded repair work. If the actual production workload has low queue sizes and very few
insertions, a sorted list could be competitive, but it should be selected only after a representative benchmark and a clear
update-cost model.

5.4 Sorting algorithms
Figure 5. Sorting algorithm timing
Measured stable insertion sort versus iterative merge sort for the seeded random arrays at three sizes.

Insertion sort takes 0.1894 ms at n = 100, 5.2688 ms at n = 500 and 54.0763 ms at n = 1,500. Merge sort takes 0.1157 ms,
0.6451 ms and 2.6409 ms at the same sizes. The gap widens markedly as the input grows: insertion sort's nested
comparisons and shifts produce O(n²) worst- and average-case work, whereas merge sort divides work into log n merge levels
and performs O(n) work per level, giving O(n log n) time. The iterative implementation uses an auxiliary array of O(n) space
but avoids recursive call depth. Both implementations are stable, preserving the relative order of equal keys (Sedgewick,
1983; Cormen, Leiserson and Rivest, 1990).
Insertion sort remains useful for very small or nearly sorted arrays because it has low setup cost, good locality and O(n)
best-case behaviour when the input is already ordered. Merge sort is a better general choice for larger unsorted batches

5.6 Network shortest-path algorithms
The Pearson distinction criterion also asks for two shortest-path algorithms illustrated with examples. A SOC network can be
modelled as a weighted directed graph: vertices represent sensors, gateways, switches and servers, and edge weights
represent a simplified traversal cost or latency. Figure 7 contains a four-vertex example. From Sensor to Server, the candidate
route through Gateway then Switch costs 2 + 1 + 5 = 8; the direct Gateway-to-Server alternative costs 2 + 8 = 10, and the
Sensor-to-Switch route costs 4 + 5 = 9. Both implemented algorithms return 8 on this non-negative graph.
Figure 7. Weighted SOC network shortest path
Illustrative positive-weight network. The highlighted route is Sensor → Gateway → Switch → Server and costs 8. The same graph is supplied
to both algorithms.

Dijkstra's algorithm repeatedly finalises the lowest-distance vertex and relaxes its outgoing edges. With an adjacency list and
a binary min-heap, its common sparse-graph bound is O((V+E) log V); the implementation uses lazy duplicate heap entries and
checks stale distances when they are removed. Its precondition is non-negative edge weights. A negative edge can invalidate
the greedy finalisation argument, so the implementation rejects negative weights instead of returning a plausible but
incorrect route (Dijkstra, 1959).
Bellman–Ford relaxes every edge repeatedly, at most V−1 rounds, and then performs one extra pass to detect a reachable
negative-weight cycle. Its O(VE) time is slower for large sparse positive-weight graphs, but it supports negative edge weights
and can detect a negative cycle, which means no finite shortest path exists for affected vertices (Bellman, 1958). The
implementation validates source nodes and edge endpoints and stops early if a pass makes no change. The tests exercise a
negative edge and a reachable negative cycle. In this SOC example, Dijkstra is the appropriate routine when network costs
are non-negative; Bellman–Ford is a more general diagnostic alternative when negative edge semantics are meaningful.

5.7 Trade-offs and three benefits of implementation independence
A key ADT trade-off is the balance between representation cost and operation guarantees. A linked queue uses additional
memory to make tail insertion and head removal O(1); a circular array queue can be more compact but has a fixed or resizing
capacity policy. An array stack is simple and fast but needs a capacity bound; a linked stack grows dynamically but allocates
nodes. A binary heap selects urgent work efficiently, but locating and reprioritising an arbitrary alert is not O(1): a production
design would need an ID-to-heap-index map or lazy invalidation/version tokens. Making those trade-offs explicit is part of
specifying the ADT rather than an afterthought (Leiss, 2007; Heineman, Pollice and Selkow, 2009).
Implementation independence provides at least three practical benefits. First, it supports substitution: a linked queue can be
replaced by a ring buffer or a durable broker adapter while callers keep the same enqueue/dequeue contract. Second, it
supports optimisation and portability: a team can choose a representation for a target runtime or workload without rewriting
every client. Third, it improves verification and reuse: tests can check the contract once and run against alternative
implementations, while consumers remain unaware of pointer, array or heap internals. A fourth benefit is clearer ownership:
the ADT boundary localises invariants and reduces accidental coupling between the SOC UI, scheduling rules and storage

6. Security, reliability and operational limitations
The prototype enforces basic data integrity: unique non-empty IDs, enumerated severity, timezone-aware timestamps,
explicit lifecycle transitions and capacity bounds. Those controls prevent several classes of accidental corruption, but they do
not provide authentication, authorisation, encryption, input provenance verification or durable audit retention. A real SOC
would need authenticated event sources, schema validation, tenant separation, access control by analyst role, tamper-evident
audit records and a defined retention policy. The current source field is descriptive metadata, not cryptographic proof that an
event came from a trusted sensor.
The dictionary and queues are process-local. A restart loses pending work; multiple service instances do not share priority
order. RLock is not a distributed lock or transaction coordinator, and callbacks are not durably retried. These limits suit the
assignment scope but must be addressed before deployment.
The next step is a durable event log and transactional repository. An asynchronous bus could deliver analyst updates with
acknowledgements, bounded retries and dead-letter handling. Horizontal scaling would require a shared broker or partitioned
scheduler with explicit ordering semantics. Metrics should include queue depth, oldest-event age, severity latency, rejected
capacity events and delivery failures; load tests should cover sustained rates and burst recovery.
Strict priority can starve routine work during a sustained incident flood. It is implemented because the assignment requires
high-severity precedence. A production scheduler may add ageing, weighted fairness or a maximum priority burst, but that
changes the ADT selection contract and must be agreed and tested explicitly.

7. Conclusion and recommendations
The backend meets the SOC scenario's two ordering requirements with separate ADTs. A linked FIFO queue retains routine
arrival order; a custom binary max-heap selects HIGH/CRITICAL alerts first and resolves ties by earliest timestamp and stable
insertion order. An array stack records analyst actions in LIFO order. An ID dictionary supports retrieval, immutable
snapshots protect records, and observer events provide in-process updates.
The implementation has 24 passing pytest tests covering normal behaviour, edge conditions, invalid input, stability, state
transitions, capacity and concurrent ingestion. The benchmark results support a nuanced conclusion: the linked queue
outperforms list front-removal at 16,000 items, but costs more traced memory; the custom heap has stronger asymptotic
scheduling behaviour than a sorted list, yet the sorted-list alternative is faster in this tested Python environment; and merge
sort scales substantially better than insertion sort on the random arrays measured. These results are not inconsistent. They
show why asymptotic analysis, runtime measurement and memory profiling should be interpreted together.
For the assignment scenario, the selected structures are justified by their operation contracts and ordering guarantees. For
production, the recommendation is to preserve those interfaces while adding durable storage, asynchronous analyst delivery,
workload-specific benchmarking, admission/back-pressure controls, metrics and a starvation policy. The ADT boundary
makes those improvements possible without exposing every consumer to the internal representation. The project therefore
meets the core brief as a tested teaching backend while making its operational limits explicit.
